# P3-1 PR 2 — backend upload: design

**Status:** approved 2026-10-23, with two revisions applied here:
- retry safety comes from an explicit `Idempotency-Key`, never from content equality;
- orphan cleanup is a tracked recovery requirement, not just a log line.

**Builds on:** P3-1 PR 1 (object storage, merged in `c4825e8`); Phase 3 plan D1 and D2 (ai-service `docs/phase3-ingestion-plan.md`).

**Goal:** a trusted path from an authenticated upload request to a durable asset record, whose security, identity and failure behaviour are explicit and testable.

## 1. Request

`POST /content/sources/{source_id}/assets/upload?file_name=<percent-encoded name>`

| Part | Rule |
|---|---|
| Body | The raw file bytes. No multipart parser is involved. |
| `Idempotency-Key` header | **Required.** 1 to 128 characters from `A-Z a-z 0-9 . _ : -`. Otherwise 400. |
| `file_name` | 1 to 255 characters, with no path separators or control characters. Its extension must match the detected type. It is stored as the display name only: **never** part of the object key. |
| `Content-Type` header | Decides nothing. A header is not proof of type. |
| Permission | `CONTENT_ASSET_UPLOAD`. The tenant comes only from the verified request context. The source must exist, must not be revoked, and must belong to the caller's tenant. A source in another tenant answers 404, exactly as a missing one does, so a source's existence is never revealed across tenants. **Platform-scoped sources are refused** (403 `PLATFORM_SOURCE_UPLOAD_NOT_SUPPORTED`), because registration lets any tenant member with this permission add to a platform source; PR 3 decides that rule. |

## 2. Limits

- **Size:** `max_upload_bytes`, default 25 MiB, valid range 1 KiB to 100 MiB. A value outside the range fails settings validation, so startup refuses it; it is never clamped silently.
- **This route only:** the request-body middleware applies `max_upload_bytes` to the upload route. Every other route keeps its 1 MiB limit.
- **Enforced while reading:** a declared `Content-Length` over the limit is refused at once (413). Bytes are also counted as they arrive, so a missing or dishonest `Content-Length` changes nothing.
- **Time:** `upload_read_timeout_seconds`, default 60, limits the total time to read the body (408). It is not just a connect timeout.

## 3. Facts come from the bytes

- **Streaming:** the body streams into a spooled temporary file (in memory up to 1 MiB, then on disk), with SHA-256 and size computed as it arrives. An empty body gets 400.
- **Type from the opening bytes**, against an allow-list:

  | Type | Signature | Extensions |
  |---|---|---|
  | PDF | `%PDF-` | `.pdf` |
  | PNG | `89 50 4E 47 0D 0A 1A 0A` | `.png` |
  | JPEG | `FF D8 FF` | `.jpg`, `.jpeg` |

  An unknown signature, or an extension that disagrees with it, gets **415**.
- **Preliminary only:** a signature is not proof that a file is valid or safe. Structural validation and parser and OCR resource limits belong to extraction (P3-2).
- **Cleanup:** the temporary file is removed on success, failure, timeout and cancellation (`finally`).

## 4. Identity and storage

- **Asset id:** `uuid5(BUILD_UPLOAD_NAMESPACE, f"{scope}:{source_id}:{idempotency_key}")`. `scope` is the tenant id. It is deterministic, which section 5 relies on.
- **Object key:** `tenants/{tenant}/assets/{asset_id}/{sha256}`. Generated by the server, and never from the file name.
- **`storage_uri`:** `s3://{bucket}/{key}`, in the private bucket from PR 1.
- **Metadata:** size, SHA-256 and the detected MIME type are recorded from the bytes.

## 5. Idempotency contract

| Situation | Behaviour | Mechanism |
|---|---|---|
| New key, valid upload | **201 Created** | New row; object stored first |
| Same key, same source, same payload | **200 OK**, the original asset | Same derived id; SHA-256 matches. The object's presence is checked (`head`); a missing object is re-stored from the identical bytes |
| Same key reused with a different payload | **409 Conflict** (`IDEMPOTENCY_KEY_REUSED`) | Same id, different SHA-256. A different payload means a different object key, so nothing is overwritten; anything the losing request stored is deleted |
| Same key, different source or tenant | Independent asset; never one from outside the caller's scope | Scope and source are part of the id derivation |
| Concurrent requests with the same key | One logical asset; no duplicate rows | The database's primary key on `content_assets.id` refuses the second insert. The loser reads the winner: same SHA-256 gives 200, a different one gives 409 |
| Process crash after the object is stored, before the commit | A retry with the same key and bytes recovers: **201** | Same id and the same object key. Re-storing identical bytes is idempotent, and the commit then succeeds. No orphan |

- **No success before both exist:** a successful response is returned only after the object is stored (SHA-256 verified by the adapter, and by the service through `x-amz-checksum-sha256`) and the row is committed.
- **No content-hash deduplication** in the upload path. Identical bytes under two keys are two assets.
- **Existing behaviour, flagged for PR 3:** `RegisterContentAssetHandler` (client-supplied `storage_uri`) returns any active asset with the same SHA-256 in the tenant, **even one from another source**. It also lets any tenant member with `CONTENT_ASSET_UPLOAD` add assets to a platform-scoped source. PR 3, which restricts that endpoint, decides both rules.

## 6. Order of operations, compensation and orphans

1. Validate the request, source and scope. Stream, hash and detect the type.
2. If the derived asset id exists: SHA-256 equal gives 200 (healing a missing object); different gives 409. Nothing more is stored.
3. `put(key, bytes, expected_sha256=...)`.
4. Insert the row and commit, then return 201.

**Compensation.** If step 4 fails, the object is deleted, unless a committed row now references that same key. That happens when a concurrent request with the same key and payload won; its object is ours, so we answer 200.
- **When compensation fails:** a structured warning is logged (correlation id, asset id, error code; never bytes, credentials or full URIs), and the counter `content_upload_orphaned_objects_total{reason}` is incremented.
- **The response stays an error.** Tests prove that a persistence failure triggers compensation, and that a compensation failure is surfaced in the log and the metric.

**Remaining window.** An object becomes an orphan when the process crashes between steps 3 and 4 **and the client never retries with the same key and bytes**.
- **Not automatic yet:** until P3-6 delivers durable reconciliation, such objects are not cleaned up automatically.
- **Tracked requirement (P3-6), recorded in the Phase 3 plan:** a reconciliation job that lists objects under the asset prefixes, compares them with `content_assets`, and deletes only objects that have no row and are older than a grace period, so that in-flight uploads are never touched. It must be safe to rerun, and the storage adapter gains listing for it.

## 7. Errors

| Status | When |
|---|---|
| 400 | Missing or invalid `Idempotency-Key` or `file_name`; empty body |
| 403 | No `CONTENT_ASSET_UPLOAD` permission; a platform-scoped source (`PLATFORM_SOURCE_UPLOAD_NOT_SUPPORTED`) |
| 404 | No such source, or a source in another tenant (indistinguishable) |
| 408 | The body was not read within `upload_read_timeout_seconds` |
| 409 | `IDEMPOTENCY_KEY_REUSED`; revoked source |
| 413 | Over `max_upload_bytes` (declared or counted) |
| 415 | Unknown signature, or an extension that disagrees with it |
| 503 | Object storage unavailable (retryable); the response says so |
| 500 | Object storage misconfigured or denied: an operator problem, not the client's |

## 8. Tests

**Unit:**
- signature detection and the extension rules;
- the limit enforced while streaming (no, false and true `Content-Length`);
- the read deadline;
- temporary-file cleanup on every path;
- id derivation and scope.

**Application:** every row of the idempotency table, with a fake storage. That includes concurrency (two requests racing on one key, same and different payloads), compensation, a failed compensation reaching the log and the metric, and healing of a missing object.

**API:** status codes, the 1 MiB limit unchanged on other routes, and permission and scope.

**Real storage (storage gate):** an upload stored in SeaweedFS and read back with its SHA-256; a replay; key reuse; an interrupted upload recovered.

**Existing gates:** the backend test suite, `postgres-gate` (the real schema; no migration is expected) and the boundary gate stay green.
