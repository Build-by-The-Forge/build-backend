# M3-F design: conversations and cited chat

**Status: proposed, for the reviewer. Nothing here is implemented.** Written against backend `a16db6d` and ai-service `0553f35`. M3-F owns `/ai/conversations` in `openapi.yaml`.

**Summary:** students get conversations the backend owns, with answers stored only once the AI step succeeds, and only with citations the backend has checked. The persistence and routes can be built now. What an answer may draw on waits for M3-D's scope filter and then M4. M3-F also defines what happens to past answers when a document they cite is deleted, as the reviewer ruled on M3-D.

## Decisions for the reviewer

| # | Decision | Recommendation |
|---|---|---|
| 1 | A repeat of a send with the same key while the first is still waiting for the AI service | Answer 409 `TURN_IN_PROGRESS` with `Retry-After`, a contract addition. Holding a database transaction open across a 60-second AI call isn't acceptable |
| 2 | Past answers that cite a document since deleted | Replace the whole assistant message with a fixed notice, and drop its citations. An answer can quote or closely paraphrase its source, so stripping excerpts alone wouldn't remove the copied text |
| 3 | Past answers citing a document the student can no longer read, without it being deleted: withdrawn, taken down, or they left a course | The same as deletion, decided when the message is read rather than stored, so it follows the one read policy from M3-D |
| 4 | The legacy `POST /ai/chat`, which returns raw context passages (G-18) | Remove `context` from it now. Retire the route once conversations ship, since the mobile app won't use it |
| 5 | A conversation's title | The first question, cut to 80 characters at a word boundary. Not generated by a model, which would cost a call and could invent things |
| 6 | Retention | Still the open product decision Decision A recorded. **Conversations aren't released to students until it's settled**, and until then `expires_at` is null |

## Ownership and storage

Decision A applies: the backend issues the IDs and owns persistence, authorization, retention and deletion.

| Table | Holds |
|---|---|
| `conversations` | Tenant, owner, title, `created_at`, `updated_at`, `expires_at`, status |
| `conversation_messages` | Conversation, a sequence number, role, content, `grounded`, `redacted`, `created_at` |
| `conversation_citations` | Message, number, asset and source IDs, title, pages, excerpt |
| `conversation_message_sources` | Message, asset, run and attempt: **every source in `sources_used`**, cited or not. IDs only, no text |
| `conversation_turn_keys` | Conversation, idempotency key, the question's SHA-256, state (`pending` or `stored`), a lease, a `generation`, and the stored turn |

- **Owned by one user in one tenant.** Anyone else, staff included, gets `RESOURCE_NOT_FOUND`. There's no staff route to read a student's conversations; that would need its own decision, as break-glass access to documents would.
- **Order:** conversations by `updated_at DESC, id DESC`, and messages by their sequence number, so a question and its answer never swap even when their timestamps are equal.
- **Never logged or sent to analytics** (PRD §231). A test captures the logs during a turn and finds no message text in them.
- **The migration** takes the next Alembic number after M3-D's 0030 and L4's outbox, whichever order those merge in.

## Sending a message

`POST /ai/conversations/{id}/messages` with an `Idempotency-Key`:

1. **Reserve**, in a short transaction: lock the conversation, then insert the turn key as `pending` with a lease and `generation` 1, or find it.
   - Already `stored` with the same question: return the stored turn, with no AI call.
   - The same key with a different question: `IDEMPOTENCY_KEY_REUSED`.
   - `pending` within its lease: 409 `TURN_IN_PROGRESS` with `Retry-After` (decision 1).
   - `pending` past its lease: take it over by incrementing `generation` and renewing the lease.
   - The request keeps the `generation` it reserved with. That's its fencing token.
2. **Ask the AI service**, outside any transaction, over the existing signed call.
3. **Check every source, then every citation** (see [Citations](#citations)). If any source the model used fails, the whole answer is withheld: `ANSWER_WITHHELD`, a 503 with `Retry-After`. Nothing is stored, the key is freed as in step 5, and the event is logged with IDs only.
4. **Store**, in one transaction, in this order:
   1. Lock the conversation. If it's been deleted, store nothing and return 404.
   2. Mark the key `stored` **only if it's still `pending` at this request's `generation`**: `UPDATE … WHERE state = 'pending' AND generation = :mine`. If that changes nothing, the request has lost its reservation (see [Fencing](#fencing)) and stores nothing.
   3. **Check every source again**, in this transaction, as described in [Revalidating at storage](#revalidating-at-storage). If any source is no longer eligible, roll the whole transaction back: no question, no answer, no citations, and the key keeps its `pending` state at this generation. Then free the key as in step 5, fenced, and return `ANSWER_WITHHELD`.
   4. Insert the question, the answer, its citations and **a source row for every entry in `sources_used`**, with the next two sequence numbers. Update `updated_at`, and the title if this is the first question.
5. **On failure** at step 2, `AI_UPSTREAM_ERROR` or `AI_UNAVAILABLE`, or a withheld answer at step 3, the key is deleted and nothing is stored. A retry asks again, and retrieves afresh.

### Fencing

A request can be slower than its lease: the AI call outlives it, another request takes the key over, and both get answers. The conversation lock orders their storage, but only the generation says which one still owns the key.

**The invariant:** a turn is stored only by the request holding the key's current generation, and a stored turn is never replaced.

| Sequence | Outcome |
|---|---|
| A reserves (generation 1). Its lease expires. B takes over (generation 2). **B stores first**, then A returns | B's turn is authoritative. A's update matches nothing, so A stores nothing and returns B's stored turn, since the question is the same |
| As above, but **A returns first**, while B is still waiting | A's update matches nothing, since the key is at generation 2. A stores nothing and answers `TURN_IN_PROGRESS`. B then stores |
| A's lease expires, and no one takes over before A returns | A still holds generation 1, so A stores. The lease decides only when a takeover is *allowed* |

- **The lease** is longer than the AI timeout plus the time to store, so a takeover normally happens only after the first request has died. The generation is what makes the rare overlap safe, not the lease's length.
- **Duplicate AI calls** are possible only in that overlap, and they're the accepted cost: at most one answer is stored, and the other is discarded.
- **Deleting the key** after an AI failure (step 5) is fenced the same way, so a stale request's failure can't free a key a newer request holds.

### Revalidating at storage

The check after generation protects the response. **The check at storage protects the history.** A document revoked between the two would otherwise be stored in a conversation.

- **The same source set is checked again inside the storing transaction**, against the one read policy and the current `denied_assets`, before anything is inserted.
- **It reads with share locks.** It locks every row the read policy reads for each source, `FOR SHARE`: the document, its publication and its rights record. **Every revocation path in M3-D writes at least one of those rows**: deletion, revocation, withdrawal, takedown, report hiding, a rights change and reclassification. So a revocation either commits first, and this check sees it, or waits until the turn has committed.
- **A revocation that commits just after the turn** is handled by [lost access](#deletion-and-lost-access). The stored message is redacted when read, and on deletion it's redacted in place. Stored history is therefore never shown with a source the reader can no longer see, whichever way the race falls.
- **Generation first, sources second**, both in the same transaction. A stale request fails on its generation before anything else, and can't store even if its sources are still eligible. A current request whose sources have lapsed stores nothing, and frees only its own generation's key.
- **The caller's own membership** is checked on every request already. The storing transaction also reads the caller's membership row `FOR SHARE`. Ending a membership updates that row, so the turn can't land after the member is gone. L4 isn't built yet. When its shared membership lock exists, the storing transaction takes that lock instead, so both use one mechanism.

- **An uncertain timeout**, where the AI service may have answered but the backend didn't hear back, stores nothing. The retry asks again, which costs a call but can't leave a half-stored turn.
- **Two different keys at once** in one conversation are both answered. The conversation lock only orders their storage.
- **Each turn is answered on its own**, as the contract says. Passing history to the AI service is a separate AI contract change.
- **Rate limits** use the existing `ai_request` throttle, with the message limited to 4,000 characters.

## Citations

The boundary design requires that the backend never forwards model output blindly.

**Every source, not only the cited ones.** This was amended after the M3-D ruling on `fe7742e`: a model can use a passage without citing it. The AI service reports `sources_used`, every `(asset, run, attempt)` whose text was retrieved for the request or reached the model. M3-D's AI PR 1 adds that field. Before anything is returned, the backend applies [M3-D's provenance check](m3-d-design.md#provenance-check) to the whole set:

- Every source must be in the caller's tenant, readable by them now, not denied and not deleted.
- **If any fails, the whole answer is withheld**, cited or not, rather than replaced with "not covered": the document may have shaped the text. A retry retrieves afresh without it.
- A response without `sources_used`, a source outside the tenant, or a citation naming a source that isn't in `sources_used` is a broken contract. The answer is withheld and an alert raised.
- **Nothing is streamed before this check passes.** The first release has no streaming.

"Not covered", with `grounded: false`, remains the answer only when the AI service itself finds the material doesn't cover the question.

Each citation is also checked, after generation:

- **The document exists in this tenant and the caller may read it now**, by M3-D's one read policy.
- **It isn't deleted, and its latest job is `ready`.** This catches a document that stopped being eligible while the answer was being generated.
- **The chunk belongs to that document's current run and attempt.** The AI service doesn't return the run and attempt today, so this needs the AI change below. Until then, the check is on the document only, and the gap is stated rather than assumed closed.

`source_id` and `title` come from the backend's own records, and pages from the AI service, nullable, never guessed.

**The excerpt needs an AI contract change.** The contract says the excerpt is "from the cited passage. Never generated". The AI service's citations carry no text, and its context items carry no chunk ID, so the backend has no reliable way to tie a passage to a citation, and guessing would break that rule. **The AI service adds the cited chunk's text, run and attempt to each citation**, in a PR M3-F owns. The backend cuts the text to 500 characters at a word boundary. Until that PR merges, no conversation route ships.

## Deletion and lost access

- **Deleting a conversation** removes its messages, citations and keys in one transaction. A turn finishing afterwards stores nothing. A repeat answers `RESOURCE_NOT_FOUND`, as the contract says.
- **A deleted document (ruling 9 on M3-D):** M3-D emits `content.document.deleted`, with IDs and no content. M3-F consumes it from the outbox and, in one transaction per message:
  - Replaces every assistant message **that used it, cited or not**, according to its source rows, with a fixed notice: "This answer used a document that's no longer available."
  - Sets `redacted: true` and deletes its citations, excerpts included.
  - Keeps the student's own question, which is their text, not the source's.
- **Lost access without deletion** (decision 3) is applied when messages are read: a message **with any source** the caller can no longer read, cited or not, is returned redacted the same way. So it follows the read policy immediately, without needing an event for every way access can end.
- **Audit records** keep message and asset IDs and the time of redaction, never the removed text.
- **The AI service holds nothing** of a conversation: it's stateless per turn, and memory is gated off.

### Every source, kept with the message

A model can use a passage without citing it, so redaction can't work from citations alone.

- **`conversation_message_sources` records the whole `sources_used` set** for each assistant message, kept separate from its citations: a source can shape an answer without appearing as one.
- **Integrity:** the message is a foreign key that cascades with it. The asset is a foreign key to `content_assets`, whose rows are never hard-deleted. `(message, asset, run, attempt)` is unique, and there's exactly one row for every entry in `sources_used`. That includes a "not covered" answer whose retrieved passages didn't suffice, since those passages still reached the model. Only an answer with an empty `sources_used` has no rows.
- **Redaction uses it, not citations.** A deletion event redacts every message with a source row for that asset. When messages are read, a message is redacted if **any** of its sources is no longer readable by the reader, cited or not. The read checks a page's sources in one query.
- **A reprocess isn't lost access.** A later run or attempt of the same document doesn't redact anything: the document is still readable, and only its access decides.
- **What redaction keeps:** the source rows stay, as IDs with no text, for audit. The message's answer text, its citations and their excerpts are removed, so no history retains source-derived content. The rows go with the conversation, under the retention policy.

**Contract changes**, in M3-F's contract PR: `ConversationMessage` gains `redacted`, and `sendMessage` gains 409 `TURN_IN_PROGRESS` and 503 `ANSWER_WITHHELD`, retryable.

## Before and after M3-D and M4

| Stage | What answers may use | Citations checked against |
|---|---|---|
| Today | Every chunk in the tenant | Nothing: they're dropped |
| After M3-D's first PR | `institutional` chunks only | The backend's read policy, and `ready` |
| After M4 | The allow-list: the caller's own `ready` documents and the institutional ones they're eligible for | The same, plus run and attempt |

**Conversations can ship after M3-D's first PR**, answering from institutional material only. Students' own documents become usable in their answers with M4. M3-F's citation check is a second line behind M4's filter, not a replacement for it.

## Acceptance tests

On migrated PostgreSQL, with the AI service's test providers in the boundary gate for the AI paths.

| Requirement | Test must show |
|---|---|
| Ownership | Another student, staff, another tenant: `RESOURCE_NOT_FOUND` on every route |
| Idempotency | The same key and question: one AI call, the same turn. A different question: `IDEMPOTENCY_KEY_REUSED`. Concurrent repeats: one call, the rest `TURN_IN_PROGRESS` |
| Abandoned turn | A request killed during the AI call: its lease expires, and a retry with the same key asks again and stores once |
| Fencing | On PostgreSQL, with the AI step held open: A's lease expires, B takes over, and each of the three orders in [Fencing](#fencing) ends with exactly one stored turn, B's where B finished first. A stale failure doesn't free B's key |
| Failure | AI down or erroring: nothing stored, the key freed |
| Ordering | Questions and answers in sequence, even with equal timestamps and concurrent turns |
| Deleted mid-turn | A conversation deleted during the AI call stores nothing |
| Sources | A document revoked while the answer was generated, whether it was cited or only used, withholds the whole answer: `ANSWER_WITHHELD`, nothing stored, the key freed (boundary) |
| Revalidation at storage | On PostgreSQL, with the turn held between the post-generation check and its commit, revoke a source by each M3-D path. The turn stores nothing: no question, answer or citations. It returns `ANSWER_WITHHELD`, and the key is free for a retry. With the revocation racing the commit instead, the outcome is either withheld, or stored and then redacted when read, never shown unredacted. A stale generation stores nothing even with every source still eligible |
| Citations | Wrong tenant, unreadable, deleted or not `ready`: the answer is withheld. A citation outside `sources_used` is withheld and alerted (boundary) |
| Excerpt | Matches the cited chunk's text, at most 500 characters, never model output |
| No internals | No chunk IDs, storage paths, tenant IDs, `memory_used` or uncited context in any response |
| Redaction | After a document's deletion, every message that used it is redacted, with no excerpt or answer text left in the database. After lost access, it's redacted when read |
| Uncited sources | On PostgreSQL, a source that was used but not cited is revoked after the turn is stored: the message is redacted when read. The same source is deleted after storage: the message is redacted in place by the deletion event. Every `sources_used` entry has a source row, and a reprocess redacts nothing |
| Logs | No message text in the logs during a turn |
| Bad input | M3-C's PostgreSQL bounds: NUL, oversized offsets, a message past 4,000 characters |

## What this design doesn't settle

- **Retention**, which blocks release to students.
- **Follow-up questions** that understand earlier turns. That's an AI contract change, not in this contract version.
- **Staff access** to a student's conversations, which is not provided.
